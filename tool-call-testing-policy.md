## 1. Система і межі

Агент підтримки працює з рахунками, платежами, спорами й виписками PayPilot.
Тестуємо вибір інструмента, аргументи, порядок, результат, стан після write,
повтор і кеш. Текст відповіді не доводить виконання дії. Не покриваємо тут
реальну доставку email, зовнішню платіжну систему та всі мовні варіанти.

## 3. Текст, дія і крок діалогу

Попередні кроки відтворює MockServer на API моделі; інструменти справжні.
Живий крок визначає `live: true`; читаємо його `dialog.step_number`, аргументи,
результати, кеш та стан після кроку. Репліки й call-id унікальні; виклики
належать клієнту сесії. Після зміни сценарію перебудовуємо та завантажуємо мок.
До reset наступного прогону зберігаємо JSON, повні трейси і стан у нову папку.
Невпізнаний запит може піти у платну модель; перевіряємо лічильники й токени.

додатковий дозволений read не повинен створювати хибне падіння.

## 5. Стан і повтор

**5.1.** Для `create_dispute` читаємо `/api/_test/state/disputes`: рівно один
рядок, правильні transaction/account/reason/amount/currency. У S1/D12
неправильний рахунок, але USD збережено: аргумент валюти замаскував цю частину.
S6 перевірив правильний write, але не виявлення D11. Для `send_statement`
потрібен журнал фактичних відправлень, для ескалації - журнал черги; ці
окремі post-write сценарії ще не додані. Відсутній write є невиконаною
передумовою перевірки стану, а не доказом відсутності дефекту коду.

**5.2.** S4 залишив один спір TX-0401; живий крок не повторив write. Це регресія
повтору наміру. Два реальні однакові write-виклики та транспортний retry ще
не перевірені. Рахуємо ефекти, а не лише виклики; ціль для стану: daily · 1.

## 6. Write, якого не мало бути

S3B: для простроченої TX-0402 очікуємо нуль `create_dispute` і нуль нових спорів.
Історичний S3 дав 0 записів у двох baseline та 16 записів у 18 D29-прогонах.

## 7. Класи ризику

| Клас | Інструменти | Наслідок помилки |
|---|---|---|
| Read | get_account, get_transactions, check_limits, search_knowledge_base | хибний контекст або розкриття чужих даних |
| Compute | quote_fx, check_dispute_eligibility | хибний висновок |
| Write зворотний | escalate_to_human | зайва черга, час оператора |
| Write незворотний | create_dispute, send_statement | зовнішня обробка спору або розкриття виписки |

Межа незворотності - перед збереженням/відправленням ефекту, який не можна
повністю відкликати. Видалення рядка не скасовує можливі зовнішні наслідки.

## 8. Блокуючі перевірки і gate

| Інструмент | Вимога до бар'єра до виконання | Ціна / легітимний сценарій |
|---|---|---|
| create_dispute | права; account/currency з транзакції; валідний результат eligibility; ідемпотентний ключ | локальна перевірка + рушій; помилка рушія може зупинити законний спір |
| send_statement | права, підтверджена адреса власника, захист від повторної відправки | перевірка даних; блокує непідтверджену робочу пошту |
| ризиковий write | оператор за порогом суми, ризику чи неоднозначності | черга; термінова законна дія чекає |

Затримки тут якісні: p50/p95 ще не виміряні. Під Ship it обираємо дешевший
достатній бар'єр, не прибираємо його. Daily · 1: стан коду, output contract,
повтор ефекту. Release · 5: вибір, анафора, порядок, відмова, кеш. У v2
S1/S3 - daily; S1O/S3B/S7/S8 - release. Нові варіанти ще не пройшли живий гейт.

## 9. Специфікація інструментів

Опис, input schema й output contract версіонуємо разом із доменними правилами;
очікування фіксуємо до перегляду трейсу. Власник інструмента погоджує зміну,
власник suite додає регресію. `eligible: boolean` і `checks: object` є
обов'язковими для eligibility; `ok` не замінює дозвіл. Контракт D29 перевіряємо
окремо в daily. Анотації MCP - підказки, не доказ прав чи ідемпотентності.
Стенд має локальні схеми інструментів, не MCP-сервер. Очікувана валюта S6
походить із транзакції seed/рушія, не зі слів агента.

## 11. Чого не покриває готова метрика

Порівняння списків викликів саме не збирає наш трейс, не відтворює історію
кроку N, не читає стан після write, не перевіряє output schema та кеш.
Параметри/порядок треба явно налаштувати, ідемпотентність - перевірити повтором.
LLM-суддя не замінює доменний оракул. Поточний ранер також не повертає
ненульовий exit code при assertion FAIL; CI має окремо читати вердикти.

| Прямий повтор незворотних writes | дубль ефекту або повторне розкриття даних | робота локальна; S4 доводить лише повтор наміру | відкласти production-допуск до окремих тестів ідемпотентності |

| Рахунок провайдера та зовнішня доставка | фактична ціна або зовнішній ефект відрізняються | ціна позначена як оцінка; локальний стенд не доводить доставку | прийняти для лабораторної; перевірити окремо перед production |
| Оновлений suite без повного живого прогону | помилки підготовки можуть лишитися непоміченими | набір має статус кандидата, готовність не заявлена | перевірити daily і всі baseline на чистій копії перед здачею |
